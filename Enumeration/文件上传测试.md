• # 文件上传漏洞通用测试逻辑

  ## 核心原则

  不要一上来直接上传反向 shell。

  文件上传测试应逐层证明：

  1. 存在真实上传点
  2. 能成功上传文件
  3. 上传文件可访问或会被后端处理
  4. 上传限制可被理解和验证
  5. 存在可利用的执行或解析路径
  6. 最后才考虑反向 shell

  反向 shell 是 RCE 已确认后的交互手段，不是上传功能的初始测试方式。

  ---

  ## 1. 确认上传点

  先确认页面或接口中是否存在真实上传功能。

  重点记录：

  - URL / endpoint
  - HTTP method
  - `Content-Type`
  - 是否为 `multipart/form-data`
  - 文件字段名
  - 其他必需字段
  - Cookie / token / CSRF
  - 上传后返回内容
  - 上传后文件路径
  - 错误提示

  建议用 Burp 抓一次正常上传请求，作为后续测试基准。

  ---

  ## 2. 先上传无害 marker 文件

  不要直接上传 webshell 或 reverse shell。

  先用无害文件验证上传行为：

  ```bash
  printf 'upload-marker-001\n' > marker.txt

  示例请求：

  curl -i \
    -F 'FILE_FIELD=@marker.txt;type=text/plain' \
    http://target/upload

  如果需要认证或特殊 header，应完整保留正常请求中的 Cookie、header 和 token。

  观察：

  - 是否允许上传
  - 是否返回错误
  - 是否返回文件名
  - 是否返回文件路径
  - 文件是否被重命名
  - 文件是否能被访问
  - 文件内容是否原样保存

  如果返回路径，尝试读取：

  curl -i http://target/uploads/RETURNED_NAME

  ———

  ## 3. 枚举上传限制

  使用无害内容测试不同扩展名。

  printf 'marker\n' > test.jpg
  printf 'marker\n' > test.png
  printf 'marker\n' > test.gif
  printf 'marker\n' > test.txt
  printf 'marker\n' > test.pdf
  printf 'marker\n' > test.php
  printf 'marker\n' > test.phtml
  printf 'marker\n' > test.phar
  printf 'marker\n' > test.php.jpg

  逐个上传并记录：

  - 状态码
  - 错误信息
  - 是否成功
  - 返回文件名
  - 实际保存扩展名
  - 是否能访问
  - 响应头中的 Content-Type

  判断过滤方式：

  - 是否是白名单
  - 是否是黑名单
  - 是否只检查扩展名
  - 是否检查 MIME
  - 是否检查 magic bytes
  - 是否大小写敏感
  - 是否允许双扩展
  - 是否重命名文件
  - 是否压缩、转码或二次处理文件

  ———

  ## 4. 测试 MIME 和 magic bytes

  如果应用声称只允许图片或特定文件类型，应分别测试：

  - 文件扩展名
  - HTTP Content-Type
  - 文件头 magic bytes
  - 文件真实内容

  示例：伪 GIF 文件。

  printf 'GIF89a\nupload-marker\n' > polyglot.gif

  上传：

  curl -i \
    -F 'FILE_FIELD=@polyglot.gif;type=image/gif' \
    http://target/upload

  目标是判断服务端到底检查了什么，而不是直接执行 payload。

  ———

  ## 5. 测试文件名处理

  在无害内容前提下测试文件名处理逻辑。

  关注：

  - 空格
  - 大小写
  - 双扩展
  - 特殊字符
  - 超长文件名
  - Unicode
  - URL 编码
  - 路径分隔符是否被过滤

  示例文件名类型：

  test.php.jpg
  test.PHP
  test.phtml
  test.phar
  test.jpg%00.php
  ../test.jpg
  ....//test.jpg

  注意：路径穿越、空字节、解析差异测试可能影响服务器文件路径，应在授权范围内谨慎进行。

  ———

  ## 6. 判断上传文件是否可访问

  上传成功后，需要确认文件的可达性。

  检查：

  - 是否返回公开 URL
  - 是否需要认证才能访问
  - 是否存在固定上传目录
  - 是否使用随机文件名
  - 是否有文件 ID 下载接口
  - 是否可通过直接路径访问
  - 是否存在预览、转换、下载功能

  常见访问方式：

  curl -i http://target/uploads/file.jpg
  curl -i http://target/download?id=123
  curl -i http://target/view?file=file.jpg

  如果文件无法访问，但会被后端处理，也仍然可能存在解析类漏洞。

  ———

  ## 7. 判断是否存在执行路径

  上传成功不等于 RCE。

  需要确认是否满足以下任一条件：

  - 上传目录允许脚本执行
  - 上传文件可被 Web 服务器解释执行
  - 应用会 include / require 上传文件
  - 应用会读取并解析上传文件
  - 应用会通过 phar://、zip:// 等 wrapper 处理文件
  - 应用会解压上传文件
  - 应用会解析 XML、Office、PDF、图片元数据等复杂格式
  - 后端任务会异步处理上传文件
  - 文件路径可控并进入危险函数

  如果上传文件只是静态下载，直接上传 reverse shell 通常没有意义。

  ———

  ## 8. 最小 RCE 验证

  只有在已经确认存在执行路径时，才进行最小 RCE 验证。

  优先目标：

  - 输出固定 marker
  - 确认当前用户身份
  - 执行只读、低影响命令

  原则：

  - 不持久化
  - 不写入额外文件
  - 不删除文件
  - 不做横向移动
  - 不做大量枚举
  - 不直接上反向 shell

  最小 RCE 的目的只是证明代码执行成立。

  ———

  ## 9. 什么时候使用反向 shell

  只有满足以下条件再考虑 reverse shell：

  - 目标明确在授权范围内
  - 上传点已经证明可控
  - 已确认存在执行路径
  - 最小 RCE 已成功
  - 需要交互式会话进行后续分析
  - 回连网络可控
  - 监听端口已准备好
  - 测试规则允许交互式 shell

  否则不要直接上传反向 shell。

  ———

  ## 推荐测试链路

  发现上传点
  -> 抓取正常请求
  -> 上传无害 marker
  -> 确认保存与访问方式
  -> 测试扩展名限制
  -> 测试 MIME / magic bytes
  -> 测试文件名处理
  -> 判断是否有后端解析或执行路径
  -> 最小 RCE 验证
  -> 必要时再使用反向 shell

  ———

  ## 常见结论判断

  ┌────────────────────────┬───────────────────────────────────┐
  │ 现象                   │ 说明                              │
  ├────────────────────────┼───────────────────────────────────┤
  │ 只能上传并下载静态文件 │ 通常不是 RCE                      │
  │ 上传目录不执行脚本     │ webshell 不会生效                 │
  │ 服务端重命名并改扩展名 │ 需要继续看解析路径                │
  │ 只检查前端限制         │ 可直接绕过前端，但仍需看后端      │
  │ 只检查 MIME            │ 可伪造 Content-Type               │
  │ 只检查 magic bytes     │ 可构造 polyglot 文件              │
  │ 允许危险扩展名         │ 需要确认是否会被解释执行          │
  │ 存在文件预览 / 转换    │ 重点看解析器漏洞                  │
  │ 存在解压功能           │ 重点看 Zip Slip、路径穿越、覆盖写 │
  │ 存在 include / phar:// │ 可能进入 RCE 链路                 │
  └────────────────────────┴───────────────────────────────────┘

  ———

  ## 一句话总结

  > 文件上传测试的正确顺序是：先证明上传和处理链路，再验证限制和执行路径；反向 shell 只在 RCE 已成立且确有需要时使用。
