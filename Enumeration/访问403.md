
• # 关于 Apache 403

  当访问某个子域名（例如 dev.siteisup.htb）返回 Apache 403 Forbidden 时，不要直接把它判断为漏洞。它首先说明该 vhost 存在访问控制边界，可能是 Apache 配置、反向代理规则、来源 IP 限制、目录权限或应用层逻辑导致的拒绝访问。

  排查思路应先建立基线：分别请求正常主域和返回 403 的子域，对比状态码、Content-Length、Content-Type、标题、响应体和响应头。如果 403 页面是 Apache 默认错误页，说明限制很可能发生在 Web Server/vhost 层；如果返回应用自定义页面，则可能进入
  了应用逻辑。

  在没有源码、配置泄露、JS 注释、备份文件、.git、文档或响应提示的情况下，发现“访问 dev 子域是否需要特殊 header”通常依赖有约束的 header fuzz / differential testing。重点不是盲目发送大量请求，而是固定 403 基线，测试常见代理、来源 IP、
  host 重写类 header，并只关注与基线不同的响应。

  常见优先测试 header 包括：

  X-Forwarded-For
  X-Real-IP
  X-Client-IP
  Client-IP
  True-Client-IP
  X-Originating-IP
  X-Remote-IP
  X-Remote-Addr
  X-Custom-IP-Authorization
  X-Forwarded-Host
  X-Host
  X-Original-Host
  X-Original-URL
  X-Rewrite-URL
  X-Forwarded-Proto
  Forwarded

  示例基线请求：
```
  curl -i http://10.129.227.227/ -H 'Host: dev.siteisup.htb'
  curl -i http://10.129.227.227/ -H 'Host: siteisup.htb'
```


  示例 header fuzz：
```
  ffuf -u http://10.129.227.227/ \
    -H 'Host: dev.siteisup.htb' \
    -H 'FUZZ: 127.0.0.1' \
    -w headers.txt \
    -mc all \
    -fs 281 \
    -rate 20
```


  其中 -fs 281 应替换为当前 403 基线响应体大小。命中信号不只看 403 -> 200，也包括响应长度变化、标题变化、Content-Type 变化、出现 Set-Cookie、跳转、登录页、debug 信息或应用错误。

  如果 fuzz 后所有 header 都没有造成差异，更可能是 Apache vhost 层面的固定 IP allow/deny 或目录权限限制。此时应转向寻找源码泄露、备份文件、配置文件、.git、可访问目录、应用入口或其他子域，而不是继续无限扩大 header fuzz。
